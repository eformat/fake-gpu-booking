= Module 2: GPU Booking App
:navtitle: Module 2: GPU Booking
:toc: macro
:toclevels: 1
:icons: font

The GPU Booking App is an OpenShift Console dynamic plugin that provides a calendar interface for reserving GPU resources. It integrates with Kueue to automatically provision per-user ClusterQueues, LocalQueues, and Hardware Profiles based on bookings.

In this module, you'll use the booking interface to reserve GPU time, observe the Kueue resources it creates, and understand the difference between reserved and consumed bookings.

== Learning objectives

By the end of this module, you'll be able to:

* Navigate the GPU Booking App in the OpenShift Console
* Create reserved bookings for different GPU resource types
* Explain the difference between reserved and consumed bookings
* Inspect the Kueue resources created by the reservation sync

== How the booking app works

image::booking-sync-lifecycle.png[Booking Sync Lifecycle,link=self,window=blank,width=700]

The booking app has three sync loops that run continuously:

[cols="1,1,3"]
|===
| Loop | Interval | What it does

| **Kueue Sync**
| 30 seconds
| Polls LocalQueues for active workloads and creates _consumed_ bookings reflecting actual GPU usage

| **Reservation Sync**
| 10 minutes
| Reads _reserved_ bookings for today/tomorrow and creates per-user ClusterQueues, LocalQueues, and HardwareProfiles

| **Expiration Cleaner**
| 10 minutes
| Gracefully drains and removes expired ClusterQueues using a two-phase approach
|===

When you make a reservation, the app creates Kueue resources that give your workloads **protected quota** -- they cannot be preempted by unreserved workloads.

== Exercise 2: Create a GPU reservation

. In the booking calendar, select today's date by clicking on it.

. Choose a GPU resource type (e.g., **H200 Full GPU**).

. Set the number of GPUs you want to reserve (start with 1).

. Click **Reserve** to create the booking.
+
The booking should appear as a colored slot in the calendar.

. Verify the Kueue resources were created:
+
[.copypaste]
[source,bash]
----
oc get clusterqueues
----
+
You should see a new ClusterQueue named after your user (e.g., `{user-user-1}`).

. Inspect your user's ClusterQueue:
+
[.copypaste]
[source,bash,subs="attributes"]
----
oc get clusterqueue {user-user-1} -o yaml | grep -A 20 "resourceGroups"
----
+
The `nominalQuota` shows the GPU resources you reserved -- this is your protected allocation.

. Check that a LocalQueue was created in your namespace:
+
[.copypaste]
[source,bash,subs="attributes"]
----
oc -n {user-user-1} get localqueues
----
+
You should see a new LocalQueue pointing to your user's ClusterQueue.

=== Verify

&#10003; Reservation appears in the booking calendar +
&#10003; User-specific ClusterQueue exists with `nominalQuota` matching your reservation +
&#10003; LocalQueue created in your namespace

== Exercise 3: Understand reserved vs. consumed bookings

There are two types of bookings in the system:

**Reserved bookings** are created when you explicitly book GPU time through the calendar. They:

* Create per-user Kueue resources (ClusterQueue, LocalQueue, HardwareProfile)
* Set `nominalQuota` that protects your allocation from preemption
* Reduce the shared `unreserved` Cohort by the reserved amount

**Consumed bookings** are automatically created by the Kueue Sync loop. They:

* Reflect actual GPU usage detected from active LocalQueue workloads
* Appear as a different color in the calendar
* Are auto-generated with deterministic IDs so the sync can reconcile additions/removals
* Can be overridden by a new reservation (consumed workloads get preempted)

. Check for consumed bookings by listing active workloads:
+
[.copypaste]
[source,bash]
----
oc get localqueues -A -o custom-columns=\
NAMESPACE:.metadata.namespace,\
NAME:.metadata.name,\
ADMITTED:.status.admittedWorkloads,\
PENDING:.status.pendingWorkloads
----

. Compare what the calendar shows with the Kueue state:
+
[.copypaste]
[source,bash]
----
oc get clusterqueues -o custom-columns=\
NAME:.metadata.name,\
COHORT:.spec.cohort,\
ADMITTED:.status.admittedWorkloads,\
PENDING:.status.pendingWorkloads
----

=== Verify

&#10003; Understand the difference between reserved and consumed bookings +
&#10003; Can correlate calendar entries with Kueue resource state

== Exercise 4: Check Hardware Profiles

When you make a reservation, the booking app also creates RHOAI Hardware Profiles so you can select your reserved GPU type when launching a workbench.

. List Hardware Profiles in your namespace:
+
[.copypaste]
[source,bash,subs="attributes"]
----
oc -n {user-user-1} get hardwareprofiles
----

. Inspect a Hardware Profile:
+
[.copypaste]
[source,bash,subs="attributes"]
----
oc -n {user-user-1} get hardwareprofiles -o yaml | grep -A 15 "spec:"
----
+
Each HardwareProfile specifies CPU, memory, and GPU resource limits that match a Kueue queue.

=== Verify

&#10003; HardwareProfiles exist in your namespace +
&#10003; Profiles match your reserved GPU resource type
