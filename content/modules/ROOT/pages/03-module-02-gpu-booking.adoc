= Module 2: GPU Booking App
:navtitle: Module 2: GPU Booking
:toc: macro
:toclevels: 1
:icons: font

The https://github.com/rhai-code/gpu-booking-app-plugin[GPU Booking App^] is an OpenShift Console dynamic plugin that provides a calendar interface for reserving GPU resources. It integrates with https://kueue.sigs.k8s.io/docs/overview[Kueue^] to automatically provision per-user ClusterQueues, LocalQueues, and Hardware Profiles based on bookings.

[IMPORTANT]
====
The Booking App was designed and built to provide a simple, intuitive interface for users to reserve GPU resources. It is a community project and actively used to manage GPU resources in real GPU enabled clusters. It is not a Red Hat product and is not officially supported by Red Hat.
====

In this module, you'll use the booking interface to reserve GPU time, observe the Kueue resources it creates, and understand the difference between reserved and consumed bookings.

== Learning objectives

By the end of this module, you'll be able to:

* Navigate the GPU Booking App in the OpenShift Console
* Create reserved bookings for different GPU resource types
* Explain the difference between reserved and consumed bookings
* Inspect the Kueue resources created by the reservation sync

[NOTE]
====
The exercises below use the **NVIDIA GB200 NVL** profile. If you are not using this profile, you will need to switch to it using the GPU Config Plugin. See the Quickstart module for more details. You may use other profiles if you wish - however you will need to adjust the commands accordingly.
====

== How the booking app works

image::booking-sync-lifecycle.png[Booking Sync Lifecycle,link=self,window=blank,width=700]

The booking app has three sync loops that run continuously:

[cols="1,1,3"]
|===
| Loop | Interval | What it does

| **Kueue Sync**
| 30 seconds
| Polls LocalQueues for active workloads and creates _consumed_ bookings reflecting actual GPU usage

| **Reservation Sync**
| 10 minutes
| Reads _reserved_ bookings for today/tomorrow and creates per-user ClusterQueues, LocalQueues, and HardwareProfiles

| **Expiration Cleaner**
| 10 minutes
| Gracefully drains and removes expired ClusterQueues using a two-phase approach
|===

When you make a reservation, the app creates Kueue resources that give your workloads **protected quota** -- they cannot be preempted by unreserved workloads.

We have configured reservation guarantees to ensure that user reservations are not preempted by unreserved workloads. This is a design choice to ensure that users can reserve GPUs for their own use and not have them taken away by other users whilst allowing unreserved workloads to run when resources are available.

Other designs are possible, the Booking App is one of many possible implementations of the Kueue Cohort model. We cover the Kueue Cohort model in more detail in Module 4.

== Exercise 2: Create a GPU reservation

[IMPORTANT]
====
**Acting as: `{user-user1}`**
====

. In the booking calendar, select today's date by clicking on it.

. Choose a GPU resource type (e.g., **GB200 NVL Full GPU**).

. Set the number of GPUs you want to reserve (lets start with **4**).

. Click **Reserve** to create the booking.
+
The booking should appear as a colored slot in the calendar. You should see 4 red colored slots in the calendar for the 4 GPUs you reserved.

. Verify the Kueue resources were created:
+
[.copypaste]
[source,bash]
----
oc get clusterqueues
----
+
You should see a new ClusterQueue named after your user (e.g., `user-{user-user1}`).

. Inspect your user's ClusterQueue:
+
[.copypaste]
[source,bash,subs="attributes"]
----
oc -n user-{user-user1} get clusterqueue user-{user-user1} -o yaml | grep -A 20 "resourceGroups"
----
+
The `nominalQuota` shows the GPU resources you reserved. You should see `nominalQuota: "4"` -- this is your protected allocation. The cpu and memo are calculated by the booking app based on the GPU resource type you reserved and are a percentage of the total resources available.

. Check that a LocalQueue was created in your namespace:
+
[.copypaste]
[source,bash,subs="attributes"]
----
oc -n user-{user-user1} get localqueues
----
+
You should see a new LocalQueue called `reserved` pointing to your user's ClusterQueue.

You can also bulk book reservations of multiple GPUs and MIG partitions by right clicking on the calendar.

image::bulk-booking.png[Bulk Booking,link=self,window=blank,width=700]

Select the number of GPUs and MIG partitions you want to reserve, add a description so other users can understand your booking and click **Book** to create the booking.

=== Verify

&#10003; Reservation appears in the booking calendar +
&#10003; User-specific ClusterQueue exists with `nominalQuota` matching your reservation +
&#10003; LocalQueue created in your namespace
&#10003; Bulk booking reservations can be created by right clicking on the calendar

== Exercise 3: Understand reserved vs. consumed bookings

There are two types of bookings in the system:

**Reserved bookings** are created when you explicitly book GPU time through the calendar. They:

* Create per-user Kueue resources (ClusterQueue, LocalQueue, HardwareProfile)
* Set `nominalQuota` that protects your allocation from preemption
* Reduce the shared `unreserved` Cohort by the reserved amount

**Consumed bookings** are automatically created by the Kueue Sync loop. They:

* Reflect actual GPU usage detected from active LocalQueue workloads
* Appear as a different color in the calendar
* Are auto-generated with deterministic IDs so the sync can reconcile additions/removals
* Can be overridden by a new reservation (consumed workloads get preempted)

Let's create some workloads to consume the GPUs we reserved and some extras to see the difference between reserved and consumed bookings.

. Deploy a simple pod requesting **6** full GPU:
+
[.copypaste]
[source,bash,subs="attributes"]
----
helm template gpu-deploy oci://quay.io/eformat/gpu-test-workloads -n user-{user-user1} \
  --set kind=Pod \
  --set name=gpu-test \
  --set replicas=1 \
  --set gpuCount=6 \
  --set gpuResourceType=nvidia.com/gpu \
  --set reserved=true \
  | oc -n user-{user-user1} apply -f-
----
+
image::book-4-gpu.png[4 GPUs Booked,link=self,window=blank,width=700]
+
You should see 2 green colored slots for the 2 GPUs you consumed and your reserved slots should now be 2 red colored slots. The Booking App refreshes screen every 10 seconds, else use the refresh button in the top right of the screen.

. Check for consumed bookings by listing active workloads:
+
[.copypaste]
[source,bash]
----
oc get localqueues -A -o custom-columns=\
NAMESPACE:.metadata.namespace,\
NAME:.metadata.name,\
ADMITTED:.status.admittedWorkloads,\
PENDING:.status.pendingWorkloads
----

. Compare what the calendar shows with the Kueue state:
+
[.copypaste]
[source,bash]
----
oc get clusterqueues -o custom-columns=\
NAME:.metadata.name,\
COHORT:.spec.cohort,\
ADMITTED:.status.admittedWorkloads,\
PENDING:.status.pendingWorkloads
----

=== Verify

&#10003; Understand the difference between reserved and consumed bookings +
&#10003; Can correlate calendar entries with Kueue resource state

== Exercise 4: Check Hardware Profiles

When you make a reservation, the booking app also creates RHOAI Hardware Profiles so you can select your reserved GPU type when launching a workbench.

. List Hardware Profiles in your namespace:
+
[.copypaste]
[source,bash,subs="attributes"]
----
oc -n user-{user-user1} get hardwareprofiles
----

. Inspect a Hardware Profile:
+
[.copypaste]
[source,bash,subs="attributes"]
----
oc -n user-{user-user1} get hardwareprofiles -o yaml | grep -A 15 "spec:"
----
+
Each HardwareProfile specifies CPU, memory, and GPU resource limits that match a Kueue queue.

=== Verify

&#10003; HardwareProfiles exist in your namespace +
&#10003; Profiles match your reserved GPU resource type
